## Локальная политика

`ApplicationRoutingPolicy` содержит `mode` и неизменяемый набор `applicationIds`.
Новые optional bridge методы `getApplicationRouting` / `setApplicationRouting`
переносят `{mode, applications}`. Запись атомарная, выполняется при отключённом
подключении. Подписки никогда не задают эти значения.

| Режим | Выбранный подтверждённый процесс | Остальной подтверждённый процесс | Неизвестный владелец |
|---|---|---|---|
| disabled | VPN | VPN | VPN |
| exclude | Напрямую | VPN | VPN |
| include | VPN | Напрямую | VPN |

DNS остаётся перед правилами приложений и проходит через VPN. Во время отказа
VPN-сервера прямые приложения могут терять разрешение имён; их маршрут нельзя
проверять только доменным запросом. При падении ядра/службы действуют прежние
правила защиты: постоянный Windows guard и Android system lockdown, если он
включён пользователем. Прямой catch-all для неизвестного процесса запрещён.

В Windows собственный dispatcher повторно устанавливает владельца socket и
точный путь процесса; UDP проверяет владельца по пакетам. В Android dispatcher
использует подтверждённый UID, отдельную обработку UDP и тот же захватывающий
все приложения TUN. DNS/control/bootstrap не получают право произвольного
прямого выхода. WFP не получает общего разрешения для пользовательских процессов.

Режим disabled сохраняет галочки без их применения. Для неизвестного старого
bridge доступны только legacy disabled/exclude; include отклоняется явно.
Legacy `setExclusions` сохраняет совместимое поведение. Старые сохранённые списки
читаются как exclude при непустом наборе, иначе disabled. Повреждение сохранённой
политики не превращается в пустой список. В Windows схема v2 остаётся owner-bound
и защищена прежними средствами хранения; v1 мигрирует с нормализацией и удалением
только дубликатов одной распознанной программы.

## Обновляемые программы Windows

Обычный идентификатор — точный путь EXE. Только для известных каналов Discord,
DiscordPTB и DiscordCanary нативный код выдаёт постоянный family anchor в том же
`Users/<user>/AppData/Local/<channel>` с соответствующим именем EXE. Это внутренний
идентификатор, а не шаблон файлов и не разрешение запускать файл в корне папки.

Меняется только сегмент `app-<числовая версия>`; другой пользователь, диск,
канал, имя, вложенная папка и helper/updater не совпадают. Проверяется реальный
образ запущенного процесса, конечный локальный путь и отсутствие reparse-выхода.
Новая активация требует существующей подходящей версии. Прежние версии одного
канала мигрируют к тому же anchor, который возвращает список приложений, поэтому
выбор в интерфейсе сохраняется. Отсутствующая программа не получает обхода.

Иконки загружаются лениво методом `getApplicationIcon({application})`: PNG64×64,
не более64KiB, ограниченные очереди и кеш, только известные/сохранённые локальные
идентификаторы. Ошибка иконки даёт нейтральный значок и не ломает список.

## Управление во время подключения

Контроллер держит последний желаемый сервер/режим отдельно от подтверждённого
нативного состояния. Устаревший запрос не перезаписывает более новый выбор.
Подтверждение команды не означает connected. Повторное подключение сериализовано;
Disconnect отменяет очередь. Резервации обновления и перезапуска сохраняются.

Windows заменяет ядро под прежним guard. Переход в PROXY допускается только для
принадлежащего этому контроллеру соединения; восстановленный неизвестный guard
не снимается. Android заменяет запрос с сохранением TUN, отменой устаревших DNS
и health-задач; PROXY на Android не появляется. Обновление политики приложений
при активном соединении пока требует обычного отключения.

## Проверки

Поведенческие unit/widget/loopback проверки, изолированный Windows controller
harness и Android emulator учитываются раздельно. Controller harness не выдаётся
за проверку установленного SCM/IPC. Общие IPv6/DNS/аварийные и физические Android
gates остаются открытыми до отдельных доказательств.

Кандидат 0.1.2+23 не опубликован. Runtime API30 выявил: legacy Kotlin callback
подтверждал только выбранные UID и скрывал невыбранные даже для include.
Ядро безопасно оставляло их в VPN, поэтому режим не соответствовал выбору.
В 0.1.3 Android подтверждает также известные невыбранные UID для include;
системные, собственный UID, неизвестные и смешанные shared UID остаются
неподтверждёнными. Проверяется appId внутри полного UID, включая рабочие профили;
изолированные процессы и SDK sandbox не получают прямой маршрут.
Смена UID выбранного пакета требует нового снимка подключения.
Регрессия проверяется отдельно на JVM и двумя реальными UID в emulator.
APK24 подтвердил include, controlled outage, exclude pair и восстановление
после обычного отключения; подробные счётчики и ограничения —
[runtime](evidence/android-routing24-runtime.json).

При замене соединения прежний TUN отменяет context до закрытия; stop ожидает
завершения UDP workers до смены снимка UID. Поздний TCP callback использует
отменённый context в ProtectedDialer. Проверено по закреплённому
`native/patches/xray-lifecycle.patch`, `native/android/dialer.go` и JNI stop;
новая ABI для этого исправления не вводилась.
