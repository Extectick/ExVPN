# Жизненный цикл gRPC и XHTTP

Задача **EXVPN-E1-011**, сборка **0.1.0+11**. Состояние исходников:
[ad9b257](https://github.com/Extectick/ExVPN/commit/ad9b2579245b68b66bc2f9364b1d7cd5d8a8192f). Платформенные результаты добавляются после
проверки конкретных пакетов; E1 в целом остаётся открытым.

## Обнаруженная ошибка

Исходный Xray `701af60772cda123492f86e383e1fdba066614a9` хранит gRPC
`ClientConn` и XHTTP `XmuxManager` в глобальных кешах процесса. Закрытие
`core.Instance` не освобождало владельца этих кешей. Windows lease в +10
закрывал принадлежащие поколению сокеты и запрещал новый DNS/Dial старому
поколению, но оставленные upstream-объекты не исчезали.

Ошибка воспроизведена через публичный ExVPN `Runtime.Close`: настоящий HTTPS
через локальный сервер, затем ожидание закрытия сокетов на стороне peer.
На исходном ядре после первого закрытого поколения оставались сокеты gRPC
h2c/TLS, XHTTP H1 packet-up и XHTTP H2 stream-one. Два других H1-сценария
в этом конкретном тесте не оставляли активного TCP-сокета; это не доказательство
отсутствия оставшихся объектов в их upstream-кеше.

Отдельный отказ REALITY-handshake у gRPC также оставлял сокет до передачи его
`ClientConn`. Его воспроизвёл synthetic TLS fatal alert; закрытие при ошибке и
отмена зависшего handshake теперь входят в регрессионные проверки.

## Изменение

Модифицированный модуль — **`v1.260327.1-exvpn.3`**, показываемая версия ядра —
**`26.10.10-exvpn.3`**. [Патч и порядок реконструкции](../native/patches/README.md).
Это собственная модификация закреплённого Xray, а не автоматическое обновление
upstream. Нативное изменение требует нового APK/установщика.

Владелец transport lifetime привязан к parsed stream configuration и завершается
из `Handler.Close`. Отмена начинается до закрытия proxy; параллельные Close
ожидают одну и ту же очистку. Кеш удаляется только для этого владельца, а
закрытие соединений выполняется после освобождения cache mutex. Завершённый
владелец не принимает новые ресурсы.

gRPC завершает свои соединения и ожидает начатые dial callbacks; запоздалый или
ошибочный сокет закрывается до возврата. XHTTP дополнительно владеет активными
HTTP-запросами, raw H1 upload, idle connections и QUIC transport. Производная
download-конфигурация разделяет lifetime родителя. Независимый экземпляр ядра
сохраняет свои соединения.

## Проверка и её пределы

Быстрые тесты выполняются на synthetic loopback без TUN, WFP или изменения
маршрутов/DNS хоста. Они проверяют кеши, реальные сокеты, зависшие запросы,
конкурентный Dial/Close, сохранение ошибок очистки и независимого живого
владельца. Сквозной тест `Runtime.Close` проверяет шесть комбинаций транспорта,
по три закрываемых поколения и один постоянно живой экземпляр с HTTPS.

Команды:

```powershell
pwsh -NoProfile -File scripts/qa/run-fast-validation.ps1 -Full
pwsh -NoProfile -File scripts/qa/test-xray-lifecycle.ps1 -Race -Count 5
```

Обычная проверка вошла отдельным набором в быстрый координатор. Race detector
остаётся отдельной проверкой и запускается в Windows CI. Сборка, исходный ZIP
и уведомления связаны Go `h1`; изменение patch или исходного архива приводит к
отказу до сборки. Offline-вход не приобретает сетевой fallback при повторном
вызове environment helper.

2026-10-17: финальная реконструированная версия прошла весь быстрый набор
и отдельный race ×5 для четырёх пакетов (26 test functions), затем `go vet`.
Stock red и итоговый результат сохранены в
[обезличенном отчёте](evidence/xray-lifecycle-build11.json).

APK обеих ABI/JVM tests, Windows service/UI/NSIS собраны локально. Аудит
[APK](evidence/android-packaging-build11.json) и
[Windows payload](evidence/windows-packaging-build11.json) подтвердил точный
module h1, полный соответствующий ZIP, patch и lock внутри комплекта notices.
На каждой платформе остаются шесть известных release blockers подписи и
полноты учёта компонентов; проверка исходников их не отменяет.

Android API30 прошёл шесть connect/disconnect в одном app/service процессе:
три gRPC h2c и три XHTTP packet-up. Независимый UID подтвердил HTTPS, после
отключения peer sockets закрылись и вернулся прямой IPv4. Cold restore и
удаление только временных тестовых данных прошли. [Отчёт](evidence/android-lifecycle-build11.json).

Первый Windows runtime +11 остановлен на первом из 15 циклов: HTTPS/DNS,
обычный UI token и восстановление TUN/WFP/routes/DNS прошли, но один peer socket
оставался после 10,86 с ожидания. Его TCP state в первом прогоне не записывался;
причину проверяет отдельный диагностический запуск. Cleanup восстановил
production binding и сеть, fixture остановлен. Этот прогон остаётся FAIL:
[доказательство](evidence/windows-lifecycle-build11-first-failure.json).

Четвёртый Windows прогон добавил положительный контроль перед отключением:
guest `Get-NetTCPConnection` и `netstat` подтвердили один Established socket
текущего SCM PID/start time, принадлежащий fixture server также видел peer.
После Disconnect в госте не осталось соединений ни одного владельца по восьми
fixture ports, но сервер сохранял один Established в 11 снимках за 10,55 с.
Прежний 10-секундный drain gate завершился FAIL (10,77 с); причина сохранения
server-side peer пока не доказана. Cleanup прошёл. Это свидетельство закрытия
клиентского socket, а не закрытие E1-011 или всей Windows lifecycle-матрицы.
[Все четыре попытки и точные хеши QA](evidence/windows-lifecycle-build11.json).
Третья попытка отдельно помечена как ошибка PS5.1 metadata parser до наблюдения
сокетов; её исправление проверено исполнением функции в PS5.1 и PS7.

Отдельная диагностика 2026-10-17 использовала QA helper с обычным TCP в том же
Sandbox, не меняя production +11 и не создавая TUN. Сравнение A/B/C задумано
для порядка закрытия socket и WFP permits. Исправлена только проверка отсутствия
LUID: [GetIfEntry2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getifentry2)
возвращает `ERROR_FILE_NOT_FOUND`. В повторной попытке A без guard подтвердил
Established с обеих сторон; gate EOF/drain прошёл за 1 мс после получения
контрольной отметки сервером. Это не полная длительность Close. B обменялся payload, но guest
не увидел файловый checkpoint сервера; C не выполнялся. Задержка получения
результата A также составила около 5 с. Это отказ синхронизации QA, а не
доказательство влияния WFP на закрытие VPN. Требуется независимое подтверждение
состояния без общего каталога во время эксперимента.

После обеих попыток проверены остановка собственных процессов, исходный
production SCM binding и service hash, отсутствие TUN/guard и точное совпадение
маршрутов/DNS. Хостовая сеть не менялась. [Отчёт](evidence/windows-teardown-diagnosis-build11.json),
[QA исходники](https://github.com/Extectick/ExVPN/commit/5ca1b3633b81f463ac8f19bd166a5c373187c22c).
Прежний Windows drain FAIL и E1-011 остаются открытыми. Авария QA helper между
Arm и записью ownership IDs не проверялась: в этом окне восстановление сохраняет
блокировку и останавливается, не удаляя неподтверждённые filters.

## Уточнение Windows: порядок удаления разрешений

2026-10-17 отдельный A/B/C запуск использовал один listener, одинаковый
синтетический payload, подтверждённый Established с обеих сторон и полностью
прочитанный echo. Теперь контроль идёт по TCP: 10-секундный monotonic gate
стартует до разрешения закрыть data socket; отдельный control socket не может
сдвинуть срок. Файлы стенда записываются после снятия guard.

- A, обычный Close: EOF и исчезновение активного peer за 26 мс.
- B, Close с действующим self-permit: EOF и исчезновение peer за 26 мс.
- C, Suspend → Close → немедленный Disarm: за 10 с EOF не получен; клиентский
  tuple отсутствует, host tuple остаётся Established во всех 381 наблюдениях.

Это выделяет порядок teardown как различающее условие на этом стенде.
Конкретный потерянный пакет или WFP event не измерялся. B сохранял permit до
получения результата host, поэтому он **не доказывает** ещё не проверенный
production порядок Close → немедленный Suspend. Последующий продуктовый fix
нужно отдельно собрать и проверить через SCM/UI с gRPC/XHTTP.

После опыта восстановлены исходный SCM binding/service hash, routes/DNS;
TUN/guard и собственные вспомогательные процессы отсутствуют. Production +11
не менялся. [Доказательство](evidence/windows-teardown-tcp-build11.json),
[QA исходники](https://github.com/Extectick/ExVPN/commit/173cdf0d99552eae5c1e8bf0e35b5c72c4d8daf5).

## Исправление контроллера Windows в +12

Контроллер сначала закрывает ядро с ещё действующим разрешением службы,
затем обязательно отзывает динамические разрешения. Persistent block остаётся
на всём протяжении. При ошибке Close или Suspend владелец сохраняется,
новое ядро не запускается, Disarm не выполняется. Только успешное явное
отключение снимает защиту; Shutdown и reconnect сохраняют её.

Параллельные Shutdown и Disconnect сериализованы перед Disarm: уже начавшая
остановку служба не теряет persistent latch из-за ожидавшей команды UI.
Искусственные задержки, linger и дополнительные разрешения не вводились.

Focused tests прошли, race ×10 — 4,16 с, vet без замечаний; независимое review
не выявило новых проблем. Общий Full: **10/10 PASS за 93,06 с**, исходники во
время тестов не менялись. [Исходники](https://github.com/Extectick/ExVPN/commit/402245f8e701610f8ef8bafc6eebe365d7c30940),
[проверка](evidence/fast-validation-build12.json). На момент фиксации этих
проверок новая сборка ещё не проходила runtime gate в Sandbox.

Последующая проверка **+12** в Sandbox прошла: upgrade +11 → +12, затем
**gRPC/XHTTP/XHTTP+REALITY ×3**, все девять циклов в одном SCM process.
Каждый цикл подтвердил HTTPS/DNS и активные sockets до Disconnect, затем
отсутствие активных host peers/client tuples, TUN/WFP и точное восстановление
маршрутов/DNS. Срок 10 с не расширялся. Независимый postcheck сверил production
binding, прежнего owner и 264 установленных файла. [Доказательство](evidence/windows-lifecycle-build12.json).

Process resources измерены, но не объявлены стабильными на неограниченном
числе циклов: handles 220 до первого ядра, 539 после девятого disconnect;
private bytes 56 045 568 → 79 503 360 (максимум 96 051 200), threads 17 → 25.
Это не доказанный memory leak и не закрытая bounded-memory приёмка. Полная
матрица E1, физический Android и другие отказы остаются отдельными задачами.

Android и Windows требуют проверки нескольких connect/disconnect в **одном
процессе**: перезапуск процесса между циклами скрывает retained globals.
Независимый probe должен подтвердить HTTPS и восстановление исходной сети,
а на Windows дополнительно проверяются отсутствие TUN/guard и неизменность
маршрутов/DNS после отключения. Эти результаты не заменяют физический Android,
полную IPv6/DNS leak matrix, sleep/resume, подпись и остальные release gates.

Upstream BrowserDialer не включён в ExVPN и не входит в контракт очистки его
внешнего browser helper. Ошибки native cleanup не объявляются успешным
освобождением ресурсов и не дают права открыть прямой fallback.
