# Windows: сохранение исключений

Дата: 2026-10-17. Задачи EXVPN-E3-004, EXVPN-E5-001/002 остаются открытыми.
Исходники хранения: [c3061b4](https://github.com/Extectick/ExVPN/commit/c3061b489608cc37b767479436a2bac16f0b5a73).
Исправление состояния после сброса и отдельный сценарий повреждения:
[fd08979](https://github.com/Extectick/ExVPN/commit/fd089794723f1db0ede022e01804b4026e90de80).
Системные проверки +4 и +5 пройдены.

## Поведение

Установленная SCM-служба сохраняет подтверждённые исключения независимо от UI.
Перезапуск службы читает тот же список. Восстановление настроек не снимает WFP:
обнаруженный после аварии guard по-прежнему переводит службу в `blocked`.
Явное отключение сохраняет список исключений для следующего подключения.

Неудачное чтение не считается пустым списком. Туннель не запускается с неизвестной
политикой. Явное отключение может освободить guard, но не исправляет и не затирает
повреждённые настройки. Пользователь может выполнить «Сбросить исключения»
в настройках после отключения VPN; ошибка записи показывается и не считается
успешным сбросом. Повторное чтение само ничего не записывает.
Успешный сброс снимает именно ошибку хранилища при отсутствии guard; восстановленная
блокировка сети и другие ошибки этим действием не снимаются.

Выбор исключений сериализован с подключением. Служба проверяет полный canonical
executable path и записывает политику до ответа об успехе/старта туннеля.
Соединение без явного списка берёт последний подтверждённый список под тем же
lock: конкурентный `setExclusions` не теряется из-за устаревшего снимка.
Изменять исключения во время подключения/активного туннеля по-прежнему нельзя.

## Хранилище

- Фиксированный ключ 64-bit HKLM: `SOFTWARE\ExVPN.ServicePolicy.v1\<owner SID>`.
  Путь хранилища не передаётся ни из подписки, ни по IPC.
- Родительский/пользовательский ключи создаются сразу с защищённой DACL.
  Разрешены только SYSTEM и Administrators. Перед чтением/записью проверяются
  владелец, protected DACL, полный набор ACE и права; подозрительный ACL не чинится
  автоматически и ключ не принимается как собственный.
- Значение `policy` типа REG_BINARY защищено **DPAPI в контексте LocalSystem**.
  `CRYPTPROTECT_LOCAL_MACHINE` не используется. Контекст приложения и owner SID
  входят в дополнительную entropy; schema и тот же SID проверяются после decrypt.
- JSON содержит только version/owner/paths. Неизвестные/повторяющиеся поля,
  неправильные типы, `null`, недопустимые пути и более 128 записей отвергаются.
  Размер plaintext ограничен 256 KiB, ciphertext — 256 KiB + 4096; чтение не
  выделяет память по непроверенному размеру значения реестра.
- Одно значение заменяется, читается обратно и вызывается `RegFlushKey` до
  подтверждения изменения. Ошибка записи/flush делает текущую политику неизвестной;
  прежний список не выдаётся как подтверждённый. После перезапуска принимается
  только целиком проверяемая запись, которая фактически сохранилась.
- Пустой список инициализируется один раз только в новом ключе пользователя и при
  отсутствии восстановленного guard. Пропавшее значение в существующем ключе —
  ошибка, а не новая установка. Сбой между созданием ключа и первой записью требует
  явного восстановления; прямой маршрут автоматически не добавляется.
- Зашифрованные предпочтения сохраняются при upgrade/uninstall, как пользовательские
  подписки. Они не содержат маршрутов/DNS/WFP и не дают обхода без работающего ядра.
  Другой installer owner использует отдельный ключ и cryptographic context.

## Проверка

Локально пройдены десять новых Go-тестов и весь модуль Windows, `go vet`, двадцать
релевантных Flutter tests и `flutter analyze`. Registry/DPAPI тесты используют
временные ключи **HKCU текущего тестового пользователя**, удаляемые после теста;
production HKLM/служба/сеть хоста не меняются.

Проверены настоящий DPAPI/registry round-trip и reopen, tamper, копирование записи
в другой owner context, неправильный тип/размер, отсутствующее ранее созданное
значение, недоверенные ACE; строгая схема, сбой записи, сохранение политики после
создания нового Controller, сохранность guard, явный сброс и сериализация connect.
Flutter tests подтверждают отсутствие автоматической записи при ошибке чтения,
явный сброс, запрет сброса при `blocked` и сообщение о неудачной записи.

На установленной **0.1.0+4** через [автоматический стенд](WINDOWS_AUTOMATED_QA.md)
подтверждены реальный LocalSystem DPAPI, сохранение выбранного в UI исключения
после hard kill SCM/restart и сохранение после явного disconnect. Все семь
протокольных сценариев и fault checks прошли; восстановлены production binding,
маршруты и DNS, TUN/guard отсутствуют. NSIS upgrade +3 → +4 прошёл с exit 0.
[Обезличенный результат](evidence/windows-policy-build4.json),
[UI после аварии](evidence/windows-policy-after-crash-build4.png).

Отдельный `windows_policy_test.dart` проверяет повреждённый ciphertext, повторное
чтение без скрытой записи, явный сброс через UI и reopen после рестарта службы.
`guest-app-policy.ps1` допускает только собственный guest/LocalSystem/owner SID,
проверяет manifests/ACL и сохраняет encrypted backup в защищённом каталоге гостя.
`run-app-policy-sandbox.ps1` восстанавливает backup и production binding в finally,
сверяет исходные маршруты/DNS и отсутствие guard/TUN. Этот сценарий не требует
подписки, fixture или Computer Use; на хосте реестр и сеть не меняются.

На **0.1.0+5** этот сценарий выполнен с настоящей установленной SCM-службой:
повреждённый DPAPI ciphertext дал `exclusions_unavailable` и видимую ошибку UI;
повторное чтение оставило ошибку, явный сброс создал подтверждённый пустой список
и состояние `disconnected` без прежней ошибки. После restart SCM/повторного запуска
QA-приложения тот же список успешно прочитан. Оба framework tests прошли.
Encrypted baseline восстановлен, маршруты/DNS совпали, guard/TUN отсутствуют,
служба Running с production binding. Upgrade +4 → +5 завершился exit 0.
[Результат +5](evidence/windows-policy-recovery-build5.json),
[ошибка до сброса](evidence/windows-policy-corrupt-build5.png),
[список после сброса](evidence/windows-policy-reset-build5.png).
Прогон +5 проверяет хранилище и UI; протокольная/fault матрица относится к +4.

Физическое отключение питания/ошибки реального диска, перенос профиля Windows и
полная матрица E1/E5 не закрываются unit tests или `RegFlushKey`.
