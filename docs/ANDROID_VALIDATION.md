# Android: проверка нативного клиента

Дата: 2026-10-16. Доказательства API36 и OTA сохранены в commit `c03e0e3`.
Дополнение API30: исходники APK [6fe2d3a](https://github.com/Extectick/ExVPN/commit/6fe2d3a288493b57ce9a7aa698a9df087f2fc50e). Это ограниченные проверки
эмуляторов, **не закрытие E1/E4 и не готовность стабильного выпуска**.

## Последние сборки и проверки, 2026-10-17

### Последующая проверка +13: Instrumentation, 2026-10-17

Неизменный APK **0.1.0+13 / exvpn.4** прошёл в отдельном API30 x86_64 эмуляторе
два gRPC h2c и два XHTTP packet-up цикла в одном процессе приложения. После
каждого Connect независимый QA UID получил HTTPS 204/200 и DNS с VPN transport;
после каждого Disconnect служба отсутствовала, Established peers на точных
fixture-портах стали равны нулю, прямой HTTPS и исходный IP hash восстановились.

Кнопками управлял отдельный Instrumentation APK через свежую семантику обычного
интерфейса. Production APK не перестраивался и не переустанавливался. В активном
VPN UIAutomator не вызывался, повторных кликов не было. Четыре цикла заняли
**50,442 с**, весь сценарий с подготовкой и очисткой — **177 с**. Connect UI
readback — 865–1674 мс; Disconnect — 150–179 мс. Это время UI-наблюдения,
а не измерение всей native teardown latency.

Синтетические группы удалены, настройки сохранены, служба/fixture остановлены,
прямой интернет восстановлен. После штатного Disconnect и всех cleanup gates
завершение самого эмулятора потребовало остановить его оставшийся процесс по
проверенным PID/path/start. Пользовательский эмулятор не изменён.
[Отчёт](evidence/android-transport-semantics-build13.json),
[снимок после четвёртого Disconnect](evidence/android-transport-semantics-build13.png),
[QA исходники](https://github.com/Extectick/ExVPN/commit/2259bb7).

Сервер fixture использовал exvpn.3, клиент — exvpn.4; общий внешний выход хоста
не доказывает туннель равенством IP. DNS success не является полным leak audit.
Физический Android, IPv6, fault/lockdown и все внешние протоколы остаются открытыми.
Прежний незавершённый UIAutomator-прогон сохранён в
[историческом отчёте](evidence/android-runtime-build13.json).

### Обновление +11 → +12 и HTTPS, 2026-10-17

В отдельном API30 x86_64 эмуляторе установлен точный APK указанного выше SHA.
Обновление при отключённом VPN сохранило UID, debug signer, два синтетических
профиля и выбор второго профиля. После cold start обеих версий снимки двух
зашифрованных namespace-файлов совпали побайтно.

Независимый UID подтвердил HTTPS **200/202 мс** и **204/240 мс** через локальный
VLESS TCP fixture: `vpnTransport=true`, оба серверных счётчика выросли. После
явного отключения восстановились прямой HTTPS и hash исходного внешнего IP.
Весь успешный сценарий занял **137,532 с**; группа удалена, собственный эмулятор,
fixture и watchdog остановлены, исходный пользовательский эмулятор не изменён.

Первая попытка остановилась до upgrade из-за CRLF в частном QA-reader; её
INDETERMINATE и cleanup сохранены отдельно. Единственный повтор выполнен после
исправления reader и семи offline-проверок. [Оба результата и привязка к сборке](evidence/android-upgrade-build12.json).
Это не проверка обновления активного туннеля, других протоколов, IPv6 или
физического устройства. APK +12 предшествует новым изменениям интерфейса подписок.

### Проверка полноты ABI

Последующий аудит точного +12 APK обнаружил `armeabi-v7a/libdartjni.so` без
Flutter engine и ExVPN core для этой ABI. Runtime API30 x86_64 выше остаётся
действительным, но пакет не следует считать пригодным для 32-битного Android.
[Состав исходного APK и воспроизведение отказа](evidence/android-abi-coverage.json).

В +13 отключено автоматическое добавление ABI закреплённым Flutter plugin;
сохраняется allowlist `arm64-v8a`/`x86_64`. Build helper и release audit проверяют
готовый ZIP: любые другие ABI и отсутствие engine/core в поддерживаемой ABI
дают отказ. Sealed helper заранее отклоняет single-ABI запрос, поскольку его
JNI/notice contract включает обе архитектуры. 38 offline packaging fixtures
PASS, включая dependency-only armv7, x86 и отсутствующий Flutter engine.
Готовый +13 APK прошёл эту проверку с обеими точными JNI/Flutter libraries:
[доказательства упаковки](evidence/android-packaging-build13.json).
Физическое устройство не проверено.

## Метод

Синтетический VLESS TCP сервер работает только на loopback хоста; эмулятор
обращается к нему через штатный шлюз Android Emulator. Реальная пользовательская
подписка не использовалась. Два собственных QA APK имеют разные UID: защищаемый
и выбранное исключение. Код находится в `scripts/qa/android-https-probe`.

Probe использует обычное системное соединение, проверяет HTTPS-сертификат и имя,
не привязывает сеть и не обходит VPN. В результатах только HTTP status, время,
счётчики, признак VPN transport и SHA256 ответа. Внешний IP проверяется на
корректный числовой формат, исходный ответ не сохраняется. UID TrafficStats
может запаздывать; нулевой счётчик не трактуется как отсутствие трафика.

Хостовый сервер и эмулятор имеют общий внешний выход. Поэтому равные внешние IP
не доказывают путь через прокси. Исключение проверено контролируемой остановкой
сервера и одновременными запросами двух UID, а туннель — также счётчиками Xray.

## Воспроизведение незакрытой аварии

На этом API36 AVD подключить синтетический профиль, включить Always-on и Block
connections without VPN в системном UI, остановить контролируемый прокси.
Получить PID только ExVPN и отправить ему SIGKILL через `run-as`; не использовать
`am force-stop`. До переключения Settings проверить service record и отдельные
probe APK. Сеть блокируется ОС, но процесс автоматически не восстановился.
В системном событии наблюдался DeadObjectException при VPN interface removal и
unbind. Это корреляция, а не доказанная причина в Android framework.
Обходы через alarm/job не добавлены.

## Матрица протоколов через Android TUN

На сборке `1ebd6d...` все семь синтетических профилей импортированы через UI из
Base64-подписки. Для каждого выбран отдельный сервер, нажата кнопка подключения,
независимый защищаемый UID выполнил HTTPS с обычной проверкой сертификата.
Показание UI Connected сопоставлено с успешным probe и увеличением счётчиков
именно соответствующего inbound сервера. Настройки доверия ОС не менялись.

| Вариант | HTTP status | Время probe | VPN transport |
|---|---|---|---|
| VLESS TCP | 204 | 1723 ms | true |
| VLESS REALITY | 204 | 1412 ms | true |
| VLESS REALITY + Vision | 204 | 6372 ms | true |
| VLESS XHTTP | 204 | 1704 ms | true |
| VLESS XHTTP + REALITY | 204 | 2362 ms | true |
| VMess TCP | 204 | 6055 ms | true |
| Shadowsocks chacha20-ietf-poly1305 | 204 | 2737 ms | true |

Время включает запуск/установление соединения и не является latency benchmark.
Сводка точных счётчиков и hash APK: [android-api36-matrix.json](evidence/android-api36-matrix.json).
Fixture: `native/android/cmd/qa-server`, только loopback, случайные эфемерные
credentials, файлы только в игнорируемой `.private`. REALITY использует локальную
camouflage TLS1.3 цель и проверку своего ключа; сертификат цели не добавляется
в системное доверие. Это не доступность реального провайдера или всех возможных
сочетаний транспорта/параметров. Семь положительных вариантов на итоговом APK
`91b014e0...` повторно не запускались: ядро/JNI между этими сборками не менялось.

Trojan и Hysteria2 через Android TUN **не проверены**: проверка TLS не отключалась
ради локального стенда. Их core-level fixtures с test-only trust — другая граница.

### Неверный ключ REALITY

На итоговом APK `91b014e0...` через QR импортирована пара синтетических профилей.
Они отличаются только публичным ключом REALITY и отображаемым названием;
endpoint, UUID и остальные параметры совпадают. Контролируемый сервер продолжал
работать в обоих случаях. Валидный профиль после появления Connected дал
независимому защищаемому UID numeric HTTPS200 за1516ms, VPN transport=true.
Первый запрос во время Connecting завершился ошибкой и успешной проверкой
не считается.

Неверный ключ привёл к состоянию Blocked / `tunnel_https_failed`. Повторный
numeric HTTPS завершился сетевой ошибкой за5572ms, VPN transport=true;
успешного прямого выхода не было. Проверка TLS/ключей и доверие ОС не ослаблялись.
Агрегатные счётчики сервера не используются как доказательство отсутствия
трафика: они могут поздно учитывать закрытие предыдущего принятого соединения.

## Реальная доставка подписанных данных на Android

Отдельный APK `debe5ac3...` собран из того же приложения, с тем же appID и native
компонентами. Только доверенная compile-time конфигурация направлена на публичный

в APK, репозиторий или снимки; обычная сборка `91b014e0...` не доверяет этому feed.
Использованы production `HttpsUpdateTransport`, проверка подписи/хеша и файловое
хранилище приложения. Проверка TLS и доверие Android не менялись.

не очищались. Восстановлен обычный APK, SHA256 установленного `base.apk` совпал
с `91b014e0...`; UI снова показал встроенные данные, stable и выключенную доставку.

SHA256 `91b014e0...`, проверенная копия для выдачи не заменялась.
Временная синтетическая OTA-подписка удалена через UI, остальные группы сохранились.
QA proxy остановлен, все семь loopback listeners отсутствуют, VPN-служба отсутствует;
независимый numeric HTTPS200 за1252ms, VPN transport=false.

Эта проверка не закрывает E6: production доставка и ключи, физическое устройство,
Shorebird, нативный release updater, а также аварии загрузки/диска и неверная подпись

## Частичный DNS capture на отдельном AVD (2026-10-17)

Перед продолжением DNS-проверки создан отдельный приватный API30 AVD.

Hop-by-Hop/MLDv2 пакет помечался усечённым. Узкий обход проверяет исходные

Первый повторный разбор
неизменного PCAP обработал все 207 пакетов, но остался **INDETERMINATE**:
один baseline DNS-ответ вышел за заранее заданное окно, fault/restoration
не завершены. Окна не расширялись задним числом; нулевое число cleartext DNS
в connected-фазе не объявляется доказательством полного отсутствия утечек.

Отдельный заранее ограниченный запуск заменил ADB reverse штатным emulator
host alias. Четыре фазы заняли **150,044 с**; новый parser целиком обработал

nonce-запроса и ответа, без выходов за окна. При подключённом VPN и после

[Отчёт с заранее заданными сроками и хешами](evidence/android-dns-directalias-build11.json).

global IPv6, физического устройства, счётчика packet drops или доказанного
TCP DNS payload. Ответы nonce не были NXDOMAIN; `no_answer` сам по себе не
используется как доказательство защиты. Предыдущий ADB-reverse отказ остаётся
INDETERMINATE и после окончательного offline reparse. Причинность его потери
ADB этим сравнением не установлена, E1-009 целиком не закрыт.

смену внешнего IP или полный DNS leak gate.

Предыдущие неуспешные попытки сохранены отдельно: deadline проверки SHA APK,
ошибочное ожидание типа поля и затем кнопки в UIAutomator. Это отказы стенда;
у них нет доказательства успешных транспортных циклов. Итоговый UI-сценарий
использовал проверенные по свежему UI-дереву семантические элементы, сохранив
независимую native cleanup и контроль владения процессами.

## Незакрытые границы

- На +13 при остановке сервера обнаружены три открытых DNS-запроса до
  Disconnect; UID не установлен. Последний strict DNS gate FAILED, детали ниже.
- Физический Android11+ и полный regression минимальной ОС; перечисленные API30
  smoke/lifecycle проверки частичные, QR-наблюдение API30-QR-001 остаётся открытым.
- Внешние Trojan/Hysteria2 и другие сочетания параметров за пределами проверенных
  вариантов; пользовательский XHTTP/REALITY подтверждён в +9, четыре новых
  Encryption/Sudoku профиля пока не подтвердили внешний HTTPS.
- Полный IPv4/IPv6/DNS packet-capture аудит с холодным DNS cache; edge cases
  неизвестного/shared UID и lifecycle установленных приложений.
- Автовосстановление после SIGKILL (наблюдавшийся API30 gap), secure pre-unlock,
  sleep/resume и полная приёмка обновления пакета.
- Подписанный release, installer, production OTA/Dart OTA и полный набор лицензий/SBOM.

Все ограничения остаются открытыми в CHECKLIST.md.

## DNS и исключения +13 (2026-10-17)

Неизменный APK +13 прошёл четыре фазы в отдельном API30 x86_64 эмуляторе:
baseline, подключение, обрыв сервера и штатное отключение. Подписка синтетическая;
исключение установлено и повторно прочитано через обычный UI. Три UID приложения,
защищённого probe и исключённого probe различаются и не разделяются другими
пакетами. Запросы двух probes последовательные, поэтому одновременная нагрузка
этим сценарием не подтверждается.

При подключении оба probe получили HTTPS 200. После остановки точного процесса
сервера защищённый numeric HTTPS отказал за 8,022 с, DNS — за 18,005 с;
исключённый numeric HTTPS получил 200 за 232 мс. VpnService оставался живым,
оба probe использовали VPN transport, поскольку direct-исключение применяется
внутри ядра. Обычный Disconnect занял 172 мс в UI и восстановил прямой HTTPS.

**Strict DNS gate FAILED.** Захват 208 198 байт содержит 1103 пакета. Во время
стабильной connected-фазы открытых UDP/TCP DNS не наблюдалось, но непрерывная
проверка от подключения до отключения включает также промежутки между фазами.
В ней найдены три UDP DNS-запроса и три ответа после остановки сервера, до
любого Disconnect. Имена совпадают с используемыми Android для connectivity
checks, однако PCAP не содержит UID. Считать отправителем ОС или исключать
эти пакеты из критерия без атрибуции нельзя. Ещё один запрос попал в переход
Disconnect; он не используется как доказательство утечки защищённого трафика.

Весь исходный запуск остаётся **INDETERMINATE**: watchdog остановил свой
эмулятор до завершения финального чтения cleanup. Значения false в исходном
cleanup означают отсутствие подтверждения. Отдельный cleanup-only за 93,589 с
подтвердил пустые подписки/исключения, отсутствие VpnService, неизменные настройки
ОС, удалённый input и отсутствие reverse; затем остановлен только принадлежащий
стенду эмулятор. Новых VPN-подключений или сетевых probes при очистке не было.
Первоначальный результат и его SHA сохранены, поздняя очистка его не заменяет.

[Обезличенный отчёт с 29 связанными доказательствами](evidence/android-dns-exclusions-build13.json),
[проверенный экран после очистки](evidence/android-dns-exclusions-build13-cleanup.png).
Координатор сверил все 29 хешей без расхождений. Следующий отдельный сценарий —
установить UID и путь открытых DNS-запросов. Global IPv6, физический Android,
счётчик packet drops и разные внешние egress этим прогоном не проверялись.

Общий offline parser теперь проверяет непрерывные интервалы, включая промежутки
между фазами. Повторный разбор исходного неизменного PCAP подтвердил шесть
открытых DNS-пакетов до Disconnect и один в переходе; это новая offline-проверка,
не новый runtime и не закрытие DNS gate.
[Отчёт](evidence/android-dns-continuous-parser-build13.json).

### Возможность определения UID, 2026-10-17

Две короткие проверки без VPN, UI и сетевых probes отделены от полного fault
сценария. Первая за 39,306 с получила `Can't find service: dnsresolver` при
`dumpsys dnsresolver querylog`; exit code 0 не принят за успешный результат.
Инвентаризация за 40,563 с уточнила: Binder перечисляет `dnsresolver` и `netd`,
но эти службы отсутствуют в `dumpsys -l`, а shell dump возвращает отказ.
Доступный `network_stack` содержит Validation logs, но не дал requester UID/PID.
Причина ограничения shell пока не установлена; наличие querylog в AOSP не
доказывает его доступность в установленном образе.

Оба запуска остановили только свой эмулятор и сохранили исходное устройство.
Координатор сверил 163 и 175 приватных файлов без расхождений. Полный attribution
сценарий не запускался: сначала нужен доступный и проверенный источник UID.
Это не новый тест отсутствия утечек и не меняет исходный DNS gate.
[Первый отказ](evidence/android-dns-uid-capability-build13.json),
[уточнённая инвентаризация](evidence/android-dns-service-inventory-build13.json).

Следующая проверка уточнила способ наблюдения: штатный `su 0` в userdebug AVD
дал доступ к querylog одному read-only процессу; обычная ADB-оболочка после
запроса сохранила UID 2000. Перезапуска ADB, изменения SELinux, приложения или
сети не было. Получен правильный заголовок журнала без записей, поэтому связь
реального DNS-запроса с UID/PID пока не проверена. После чтения ошибка имени
PowerShell-переменной остановила обвязку; первоначальный INDETERMINATE сохранён,
исправленный сценарий не запускался повторно. Очистка подтвердила остановку
только своего гостя.

Исходники Android 11 объясняют наблюдение: shell разрешено перечислять службы,
но запрещён `find` для dnsresolver/netd. Это сильное соответствие наблюдениям,
а не снятый runtime AVC. NetworkMonitor также может использовать конкретную
физическую сеть; это не устанавливает отправителя прежних трёх DNS-запросов.
[Раздельные факты запуска](evidence/android-dns-privileged-observer-build13.json),
[закреплённые AOSP-источники](evidence/android-dns-observer-source-findings-build13.json).

Положительный контроль UID пока не выполнен: подготовка остановилась до DNS
probe и querylog на сериализации числовых ключей netId в JSON. Отдельная копия
private QA исправляет только две внешние JSON-проекции; replay на фактическом
сохранённом network dump подтвердил запись и точное обратное чтение. Повторного
runtime нет, исходный INDETERMINATE и прежний DNS gate сохранены.
[Отказ до сетевого вызова](evidence/android-dns-positive-control-attempt-build13.json),
[offline replay](evidence/android-dns-control-serialization-replay-build13.json).

Следующий отдельный запуск с исправленной JSON-проекцией подтвердил контроль
владельца DNS за **59,230 с**, включая остановку своего эмулятора. Один обычный
вызов `dnsNonce` и две выборки querylog дали ровно одну новую запись нужного UID;
совпали независимо наблюдаемый PID, физический netId и окно завершения запроса.
Наблюдатель `su 0` не менял UID приложения или adbd. Ответ probe — `no_answer`,
не доказательство NXDOMAIN; имя в querylog маскируется, связи с полным wire nonce
нет. VPN не запускался. Настройки и защищённое хранилище не изменились,
свой эмулятор остановлен, исходное устройство сохранено. Координатор сверил
446 файлов доказательств по размеру и SHA-256.
[Подтверждённый контроль](evidence/android-dns-positive-control-confirmed-build13.json).
Это позволяет наблюдать новый VPN/fault-сценарий, но не устанавливает владельцев
пакетов из прежнего PCAP и не закрывает DNS gate.

Первый новый attribution-сценарий сохранил **INDETERMINATE**: baseline с обычным
UID, DNS querylog и numeric HTTPS прошёл, затем private PowerShell-скрипт попытался
выполнить `true` как команду вместо значения `$true`. Ошибка произошла до Connect;
VPN и обрыв не запускались. В PCAP только baseline (128 пакетов), protected
interval отсутствует. Весь запуск — 267,316 с, захват — 37,420 с. Все 12 проверок
cleanup прошли; исходное устройство и 42 запечатанных входа сохранены. Координатор
сверил 843 файла доказательств. [Исходный отказ](evidence/android-dns-attribution-preconnect-build13.json)
не считается ошибкой VPN и не заменяется результатом последующих запусков.

Следующая попытка подтвердила baseline и connected: HTTPS защищённого и
исключённого UID, положительный DNS через VPN, контроль UID/PID/netId и обмен
fixture. До имитации обрыва guard обнаружил пустой путь в сохранённой identity
тестового сервера и остановил сценарий. Обрыв не выполнялся. Весь запуск —
287,513 с; capture 60,817 с содержит десять открытых UDP53 пакетов с пока
неустановленным владельцем и заканчивается до cleanup Disconnect. Это
**INDETERMINATE**, а не проверка отсутствия DNS-утечек.

Исходный cleanup ошибочно считал несовпадение identity завершением fixture.
Отдельная очистка подтвердила PID/start/path/hash и уникальную командную строку,
после чего завершила только свой сервер; исходный отчёт сохранён. Disconnect,
восстановление настроек/исключений и остановка своего гостя подтверждены.
Координатор сверил 917 файлов, включая отдельное доказательство очистки.
[Connected-проверка и незавершённый fault-сценарий](evidence/android-dns-attribution-connected-build13.json).

После исправления полной fixture identity новый ограниченный запуск завершил
**все четыре функциональные фазы за 369,283 с**. Connected подтвердил HTTPS,
DNS, VPN transport и обмен сервера. После остановки точного процесса через
удерживаемый handle защищённый numeric HTTPS отказал за 8,015 с, DNS — по
deadline 18,004 с; исключённый UID получил HTTPS за 226 мс. Служба оставалась
активной. Штатный Disconnect восстановил прямой HTTPS обоих UID и исходные IP.

Непрерывный capture 146,954 с покрывает весь консервативный защищённый интервал,
включая переходы и промежутки между фазами: **9 UDP53 пакетов, 0 TCP53**.
В именованных connected/fault фазах открытого DNS нет, но общий строгий DNS gate
остаётся **false**; выбор только этих фаз дал бы неполную картину. Исходный
отчёт не устанавливает UID этих пакетов; результат — INDETERMINATE. Все cleanup
проверки прошли; координатор сверил 986 файлов. Новых сборок/установок и изменений
сети хоста не было. [Полный сценарий и ограничения](evidence/android-dns-fault-continuous-build13.json).
IPv6, DNS исключённого приложения и физический Android остаются непроверенными.

Отдельная offline-корреляция связала три из пяти DNS-запросов с NetworkMonitor:
совпали полное имя в приватном журнале, ограниченное окно времени, единственная
native PID/netId-запись, четыре снимка процесса и карты физической сети. Два
запроса остаются неоднозначными. Первый появился через 408 мс после начала
Connect, уже после native-события создания VPN; второй — в переходе Disconnect.
Эти переходы не считаются разрешением на прямой DNS. UID на самом проводе не
измерен, исходный интервал и **strict=false** сохранены. Координатор и отдельный
reviewer сверили 30 связанных файлов addendum. Прежние запуски не получают
атрибуцию задним числом. [Корреляция и её границы](evidence/android-dns-attribution-addendum-build13.json).
