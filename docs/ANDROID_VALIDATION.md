# Android: проверка нативного клиента

Дата: 2026-10-16. Доказательства API36 и OTA сохранены в commit `c03e0e3`.
Дополнение API30: исходники APK [6fe2d3a](https://github.com/Extectick/ExVPN/commit/6fe2d3a288493b57ce9a7aa698a9df087f2fc50e). Это ограниченные проверки
эмуляторов, **не закрытие E1/E4 и не готовность стабильного выпуска**.

## Стенд и сборки

без загрузки/записи snapshot. Маршруты, DNS и firewall Windows-хоста не менялись.
Дополнительно проверен Android11/API30 Google APIs rev16, x86_64, профиль Pixel4a
в отдельном read-only AVD с WHPX. Подтверждены базовое соединение и отказ сервера;
полная минимальная regression и физическое Android-устройство не проверены.

## Метод

Синтетический VLESS TCP сервер работает только на loopback хоста; эмулятор
обращается к нему через штатный шлюз Android Emulator. Реальная пользовательская
подписка не использовалась. Два собственных QA APK имеют разные UID: защищаемый
и выбранное исключение. Код находится в `scripts/qa/android-https-probe`.

Probe использует обычное системное соединение, проверяет HTTPS-сертификат и имя,
не привязывает сеть и не обходит VPN. В результатах только HTTP status, время,
счётчики, признак VPN transport и SHA256 ответа. Внешний IP проверяется на
корректный числовой формат, исходный ответ не сохраняется. UID TrafficStats
может запаздывать; нулевой счётчик не трактуется как отсутствие трафика.

Хостовый сервер и эмулятор имеют общий внешний выход. Поэтому равные внешние IP
не доказывают путь через прокси. Исключение проверено контролируемой остановкой
сервера и одновременными запросами двух UID, а туннель — также счётчиками Xray.

## Воспроизведение незакрытой аварии

На этом API36 AVD подключить синтетический профиль, включить Always-on и Block
connections without VPN в системном UI, остановить контролируемый прокси.
Получить PID только ExVPN и отправить ему SIGKILL через `run-as`; не использовать
`am force-stop`. До переключения Settings проверить service record и отдельные
probe APK. Сеть блокируется ОС, но процесс автоматически не восстановился.
В системном событии наблюдался DeadObjectException при VPN interface removal и
unbind. Это корреляция, а не доказанная причина в Android framework.
Обходы через alarm/job не добавлены.

## Матрица протоколов через Android TUN

На сборке `1ebd6d...` все семь синтетических профилей импортированы через UI из
Base64-подписки. Для каждого выбран отдельный сервер, нажата кнопка подключения,
независимый защищаемый UID выполнил HTTPS с обычной проверкой сертификата.
Показание UI Connected сопоставлено с успешным probe и увеличением счётчиков
именно соответствующего inbound сервера. Настройки доверия ОС не менялись.

| Вариант | HTTP status | Время probe | VPN transport |
|---|---|---|---|
| VLESS TCP | 204 | 1723 ms | true |
| VLESS REALITY | 204 | 1412 ms | true |
| VLESS REALITY + Vision | 204 | 6372 ms | true |
| VLESS XHTTP | 204 | 1704 ms | true |
| VLESS XHTTP + REALITY | 204 | 2362 ms | true |
| VMess TCP | 204 | 6055 ms | true |
| Shadowsocks chacha20-ietf-poly1305 | 204 | 2737 ms | true |

Время включает запуск/установление соединения и не является latency benchmark.
Сводка точных счётчиков и hash APK: [android-api36-matrix.json](evidence/android-api36-matrix.json).
Fixture: `native/android/cmd/qa-server`, только loopback, случайные эфемерные
credentials, файлы только в игнорируемой `.private`. REALITY использует локальную
camouflage TLS1.3 цель и проверку своего ключа; сертификат цели не добавляется
в системное доверие. Это не доступность реального провайдера или всех возможных
сочетаний транспорта/параметров. Семь положительных вариантов на итоговом APK
`91b014e0...` повторно не запускались: ядро/JNI между этими сборками не менялось.

Trojan и Hysteria2 через Android TUN **не проверены**: проверка TLS не отключалась
ради локального стенда. Их core-level fixtures с test-only trust — другая граница.

### Неверный ключ REALITY

На итоговом APK `91b014e0...` через QR импортирована пара синтетических профилей.
Они отличаются только публичным ключом REALITY и отображаемым названием;
endpoint, UUID и остальные параметры совпадают. Контролируемый сервер продолжал
работать в обоих случаях. Валидный профиль после появления Connected дал
независимому защищаемому UID numeric HTTPS200 за1516ms, VPN transport=true.
Первый запрос во время Connecting завершился ошибкой и успешной проверкой
не считается.

Неверный ключ привёл к состоянию Blocked / `tunnel_https_failed`. Повторный
numeric HTTPS завершился сетевой ошибкой за5572ms, VPN transport=true;
успешного прямого выхода не было. Проверка TLS/ключей и доверие ОС не ослаблялись.
Агрегатные счётчики сервера не используются как доказательство отсутствия
трафика: они могут поздно учитывать закрытие предыдущего принятого соединения.

Настройки показывают «Подключения: 1». Экран версий отображает приложение

## Реальная доставка подписанных данных на Android

Отдельный APK `debe5ac3...` собран из того же приложения, с тем же appID и native
компонентами. Только доверенная compile-time конфигурация направлена на публичный
синтетический beta QA feed с отдельным Ed25519-ключом. Приватный ключ не входит
в APK, репозиторий или снимки; обычная сборка `91b014e0...` не доверяет этому feed.
Использованы production `HttpsUpdateTransport`, проверка подписи/хеша и файловое
хранилище приложения. Проверка TLS и доверие Android не менялись.

| Сценарий | Наблюдение |
|---|---|
| Check/stage при активном VPN | Подготовлена ревизия 1, загружен 1 файл; Apply disabled и некликабелен, есть объяснение. После stage независимый HTTPS200 за1206ms, VPN transport=true, UI всё ещё Connected |
| Явное отключение | После подтверждённого Disconnected Apply стал доступен; updater сам VPN не отключал |
| Cancel | Подготовленный набор отменён, активные данные остались встроенными |
| Повторный stage/apply | Применена ревизия 1, показана новая синтетическая QA справка; commit присутствует в beta-хранилище |
| Холодный запуск | Force-stop/restart восстановил ревизию 1 и проверенную справку; подписки сохранились |
| Replay ревизии 1 | Повторная проверка показала «Новой подписанной ревизии нет» и сохранила рабочие данные |
| Откат новой ревизией | После публикации подписанной ревизии 2 с rollbackOf=1 UI загрузил 1 файл и применил исходный текст справки; счётчик ревизии увеличился до2 |
| Холодный запуск после отката | С диска восстановлены ревизия 2 и исходная справка; повторный check сообщил об отсутствии новой ревизии |

Между получением ревизий 1 и 2 APK не переустанавливался: менялся только пакет
справки. Это подтверждает OTA данных; Dart/Flutter code push, ядро и системные
компоненты так не обновлялись. У этой интеграции только один разрешённый ресурс,
поэтому переиспользование неизменённых файлов отдельно проверяется тестами пакета.

После испытания процесс остановлен, удалён только проверенный каталог
`files/signed-data-v1/beta` внутри sandbox приложения. Подписки и Android Keystore
не очищались. Восстановлен обычный APK, SHA256 установленного `base.apk` совпал
с `91b014e0...`; UI снова показал встроенные данные, stable и выключенную доставку.
Обычная сборка без QA defines повторена: стандартный `app-debug.apk` имеет тот же
SHA256 `91b014e0...`, проверенная копия для выдачи не заменялась.
Временная синтетическая OTA-подписка удалена через UI, остальные группы сохранились.
QA proxy остановлен, все семь loopback listeners отсутствуют, VPN-служба отсутствует;
независимый numeric HTTPS200 за1252ms, VPN transport=false.

Эта проверка не закрывает E6: production доставка и ключи, физическое устройство,
Shorebird, нативный release updater, а также аварии загрузки/диска и неверная подпись
на устройстве остаются отдельными критериями. Сводка:
[android-signed-data-ota.json](evidence/android-signed-data-ota.json).

На отдельный чистый API30 AVD установлен тот же обычный APK `91b014e0...`;

Работал тот же loopback-only fixture без изменения сети Windows-хоста.

### Открытое наблюдение API30-QR-001

Путь воспроизведения: «Добавить подписку» → «QR из изображения» → системный
DocumentsUI → Downloads → синтетический PNG. Файл виден как PNG image, enabled=true,
но adb tap по центру строки/плитки из свежей UI hierarchy оставляет тот же picker;
результат выбора через tap не подтверждён. Так же не открылся каталог Download при
tap внутри storage-root, хотя toolbar, выбор roots и Grid/List переключались.
Кнопок «Открыть/Выбрать» в полученном дереве не было. Отмена вернула диалог ExVPN
без ошибки. В ограниченном scoped DocumentsUI log не обнаружены Exception или
Permission Denial; это не доказывает отсутствие всех ошибок.

Сохранены [состояние до](../design/qa/android-api30/qr-picker-before.png) и
[после](../design/qa/android-api30/qr-picker-after.png) выбора. На них только
общедоступный синтетический QR с фиктивным доменом, не рабочий VPN credential.
Дополнительная короткая проверка клавиатурой успешна: один TAB установил focus
на `DocumentsUI item_root` именно этого PNG (сверено по свежему дереву), ENTER
вернул приложение. ExVPN показал «QR-код прочитан», ожидаемый синтетический
VLESS-текст и предложил подтвердить импорт; автоматического добавления не было.
Диалог затем отменён. Таким образом, native возврат файла и QR decode на API30
работают при клавиатурном выборе; дефект URI permissions не подтверждён.
Наблюдение сужено до touch/adb-взаимодействия с DocumentsUI. Его точная причина
не установлена, обычное касание на устройстве ещё нужно проверить. Исходники
приложения из-за этого наблюдения не менялись; безопасность чтения произвольных
provider URI исследуется отдельно и этим benign-файлом не подтверждается.

## Новый Android picker: ограничение до чтения (2026-10-16)

В `file_selector_android 0.5.2+11` обнаружено чтение/копирование provider-файла
до Dart-проверки размера. Android переведён на собственный `ACTION_OPEN_DOCUMENT`
и фоновый reader: максимум 5 MiB фактических байтов, deadline 20 секунд,
отдельные cancel/close, один process-wide worker. Зависший provider удерживает
свой слот; повторный запрос не создаёт новые зависшие потоки. Сырые provider
