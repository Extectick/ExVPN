# Проверка реальной подписки, сборка 0.1.0+7

Дата: **2026-10-17** (UTC проверки — 2026-10-16). Исходная ссылка, ответы,
HWID, адреса и ключи находятся только в `.private/`. Пользователь предоставил
вторую подписку для этой проверки. Её текущий ответ содержит **32 VLESS-записи**;
Trojan, Hysteria2, VMess и Shadowsocks в этом ответе не обнаружены.

## Что исправлено

- Добавлен стандартный отпечаток TLS `qq`, присутствующий в закреплённом Xray.
  Одинаковая проверка действует в Dart и нативном адаптере. Проверка сертификата
  не отключается и неизвестные отпечатки по-прежнему отвергаются.
- gRPC URI `mode=gun` нормализуется в обычный gRPC без multiMode. Произвольный
  другой режим не отбрасывается молча. Повторный импорт такого же профиля без
  явно указанного режима получает тот же ID.
- Загрузчик распознаёт запрос HWID и лимит устройств до разбора тела. Провайдер
  может вернуть служебный VLESS URI с HTTP 200 вместо подписки; такой ответ
  больше не попадает в список серверов.

## HWID

Идентификатор относится к **установке ExVPN**, а не к серийному номеру устройства.
Случайный 256-битный секрет хранится в Android Keystore-backed storage / Windows
current-user DPAPI. Для каждого HTTPS origin рассчитывается отдельный HMAC-SHA256:
другие провайдеры получают другие значения, смена токена подписки его не меняет.
Повреждённое хранилище не вызывает тихую генерацию новой личности. Удаление данных
приложения или переустановка с потерей хранилища создаст новую установку; старую
запись устройства при необходимости удаляет пользователь у провайдера.

Первый запрос не передаёт HWID. При `x-hwid-not-supported: true` загрузчик отменяет
чтение служебного тела и повторяет **тот же HTTPS URL один раз**, в пределах исходных
15 секунд. Redirect запрещён, лимит тела 2 MiB сохранён. Повторное отклонение,
недоступность защищённого хранилища и лимит устройств имеют отдельные безопасные
коды и сообщения. Сырые заголовки, URL и ID в сообщения не включаются.
Современный `x-hwid-max-devices-reached` имеет приоритет. Старый `x-hwid-limit`
вместе с `x-hwid-not-supported` трактуется как запрос идентификатора: именно
такой ответ наблюдался у данного провайдера.

Источники: [контракт Remnawave](https://github.com/remnawave/panel/blob/main/docs/features/hwid-device-limit.md),
[стандарт VLESS URI](https://github.com/XTLS/Xray-core/discussions/716),
[отпечатки закреплённого Xray](https://github.com/XTLS/Xray-core/blob/701af60772cda123492f86e383e1fdba066614a9/transport/internet/tls/tls.go).
Это ссылки на документацию; совместимость конкретного ответа проверена отдельно.

## Полученный список и реальный трафик

| Вариант | Импортировано | HTTPS 204 через локальный SOCKS ядра |
|---|---:|---:|
| VLESS / XHTTP / REALITY | 9 | 3 |
| VLESS / TCP / REALITY / Vision | 10 | 0 |
| VLESS / gRPC / REALITY / gun | 7 | 0 |

Итого импортируются **26 из 32**. Остальные шесть отклонены явно:
четыре требуют VLESS encryption `mlkem768x25519plus` с FinalMask `sudoku`,
которые ещё не представлены в строгой модели ExVPN; две задают Vision при
`security=none` и `encryption=none`. Отбрасывать параметры или незаметно ослаблять
проверку ради импорта запрещено. Эти записи не отмечены рабочими.

Все 26 принятых записей проверены настоящим HTTPS-запросом через авторизованный
loopback SOCKS закреплённого ядра. У 23 соединение HTTPS не установилось. Это
результат в конкретной сети и в конкретное время, а не утверждение о постоянной
неработоспособности провайдера. TCP-доступность сама по себе ничего не доказывает.
Отдельная диагностика смогла открыть TCP к каждому из этих 23 endpoint; причина
отказа последующего HTTPS/прокси-транспорта пока не установлена.
Этот первоначальный прогон не менял маршруты, DNS или firewall хоста.

Три успешно проверенных XHTTP-профиля затем прошли отдельный Windows-прогон:
установка +6 → +7 в Sandbox, **medium token без административных прав**, настоящий
Flutter UI → установленная LocalSystem-служба → TUN, независимый HTTPS 200/204,
DNS через TUN и рост счётчиков. Внешний IPv4 каждого профиля отличался от прямого
выхода. Подписка импортировалась из сохранённого приватного ответа; загрузка URL
через Windows UI этим прогоном не проверена. Явное отключение и cleanup восстановили
fingerprint маршрутов/DNS, production client binding; TUN и WFP latch отсутствуют.

На **Android API30 x86_64 emulator** установлен обычный debug APK +7 с сохранением
данных +6. Через обычный экран введён настоящий HTTPS URL: приложение само создало
защищённый ID, выполнило HWID-обмен и импортировало 26 профилей. Один XHTTP/REALITY
профиль проверен независимым UID `ru.exvpn.netprobe`: HTTPS 200/204,
`vpnTransport=true`, другой внешний IPv4, DNS с A/AAAA-ответами. После явного
отключения восстановились прежний IPv4 и `vpnTransport=false`. После холодного
запуска сохранились группа и 26 записей; интерфейс сообщает о шести отклонённых.

IPv6 HTTPS-запрос на Android завершился `network`; доступность IPv6 через этот
профиль не подтверждена. Ручное обновление после холодного запуска сохранило
прежний список и показало отказ обновления; точная причина в этом UI-прогоне не
снята. Неполные ответы с ошибками разбора намеренно не заменяют рабочую подписку
автоматически. Это не считается успешным обновлением.

## Доказательства и границы

- [Обезличенная матрица и хеши сборок](evidence/provider-build7.json).
- [Windows UI с активным реальным подключением](evidence/windows-provider-build7.png)
  — имена заменены до импорта; снимок сделан при прокрученном списке.
- `flutter analyze`: без замечаний; **155 app tests**, включая HWID, отмену,
  тайм-аут, безопасные ошибки, сохранность последнего списка и реальный DPAPI.
- **116 domain tests**; core/Android/Windows Go tests и vet пройдены.
- Обычные Windows release / Android debug, обе Android JNI ABI собраны.
- Отдельный live-тест настоящего Dart-загрузчика с сохранённым ID стенда подтвердил
  один HWID challenge, HTTP без mock и разбор 26 профилей / 6 ошибок. Он не заменяет
  отдельно проверенное создание ID в обычном Android-приложении.

Пакеты — **development**, Windows unsigned, Android подписан debug-ключом.
E1/E4/E5/E7 не закрываются: остаются остальные варианты и отказы, packet-level
DNS/IPv4/IPv6 leak checks, физический Android, полная матрица систем и выпуск.
При следующем прогоне нужен новый runId; нельзя брать старые `passed` из output.

Для повторения Windows-проверки используется `scripts/windows/prepare-app-sandbox.ps1`
с `-Unelevated -ProviderMatrix`, затем `scripts/windows/run-app-provider-sandbox.ps1`.
Требуются обычная установленная версия того же build, изолированный read-only input
и узкий private mapping из [методики Sandbox](WINDOWS_AUTOMATED_QA.md). В private
mapping находятся `provider-subscription.txt` с заранее заменёнными именами
`Provider node N` и `provider-cases.json` со списками `imported` / `selected`.
Тест не сохраняет изображения диалога с исходными данными и не останавливает
внешние серверы. Runner всегда восстанавливает production binding и проверяет
сеть гостя. Полный проход выбранных трёх случаев не выдаётся за проход всех 32.
