# Полные обновления Windows

## Исправление установленного updater, 2026-10-19

На машине пользователя установлена **0.1.3+24**. Скачанный 0.1.4+25 имеет
верные размер и SHA-256. Подготовительный запуск worker без commit вернул
`handoff_failed`, не закрывая UI и не запуская установщик. Причина: генератор
создаёт `handoff-` + 32 hex (40 символов), а прежний worker требовал 39.
Проверка имени исправлена через общий генератор/валидатор; ACL, точные физические
пути, владелец процесса, подпись manifest и хеш установщика сохраняются.
Добавлены регрессии реального generated path, locked-stage и pipe-handshake
тестового дочернего EXE. Реальный установленный upgrade остаётся отдельным gate.

Исправление опубликовано в **0.1.5+26 Preview**, source c7e169a3. Source/release CI,
пакет и Windows Ed25519 feed проверены. [Аудит](evidence/release-v0.1.5.json).
Для старого неисправного helper нужен один ручной переход. На этой машине
координатор закрыл старый UI встроенной native-командой без принудительного
завершения и установил публичный 0.1.5+26 через UAC. Новая версия открыта,
service Running, установленный helper check — exit0/upToDate.
[Bootstrap](evidence/windows-bootstrap26-local.json).

Отдельно подтверждён реальный установленный `restart-ui`: helper accepted,
старый UI завершился, detached worker открыл новый UI, служба продолжила работу.
[Restart](evidence/windows26-installed-restart.json). Это проверка handoff/restart,
а не полный автоматический цикл установки следующего подписанного пакета;
EXVPN-E6-008/006 остаются открытыми до такого цикла.

### Контекст запуска диагностического стенда

Прямой запуск CLI из Codex наследовал перенаправление новых AppData-папок в MSIX
LocalCache даже при `GetPackageFamilyName=NO_PACKAGE`. Существующий update-cache
открывался по обычному физическому пути, новые handoff-папки — по другому;
`finalPath` правильно отклонял это как `cache_unavailable`. ACL и длина имени
не были причиной этого отдельного отказа. Native-проверки не ослаблялись.

Установленный restart проверен из обычного Explorer-процесса без повышения прав.
Для такого запуска нужен именно desktop broker существующего Explorer:

```powershell
$exvpnShell = New-Object -ComObject Shell.Application
$exvpnWindows = $exvpnShell.Windows()
$exvpnDesktopHwnd = 0
$exvpnDesktop = $exvpnWindows.FindWindowSW(0, 0, 8, [ref]$exvpnDesktopHwnd, 1)
$exvpnDesktop.Document.Application.ShellExecute(
  'C:\Program Files\ExVPN\exvpn.exe', '', '', 'open', 1)
```

Обычный `$exvpnShell.ShellExecute` не гарантировал Explorer-parent. Для CLI-проб
desktop broker запускает отдельный обычный runner; затем уже он запускает helper.

Запись ниже описывает первоначальное внедрение. Проверка available/ready сама
по себе не подтверждает handoff → UAC → установка → новый процесс.

Реализация 2026-10-18, кандидат **0.1.0+21**. Исходники: [5b41a1c](https://github.com/Extectick/ExVPN/commit/5b41a1c070aa1d19675d9af3aabb1939a097fe98).
Это отдельный механизм от OTA данных и Shorebird. Его наличие не закрывает
приёмку E1/E6/E7 и не делает development-пакет стабильным выпуском.

Базовая установка +20 → +21 выполнена, приложение открыто; service Running,
installed helper check — exit0/upToDate. Итоговый Full 12/12 PASS за 86,49 с,
284 app tests; source fingerprint неизменен. [Доказательства](evidence/windows-app-updater-build21.json).
Аудит распакованного NSIS подтвердил payload и 145 notices, но сохраняет пять
release blockers: unsigned/development package, не закреплённый издатель,
незавершённые Flutter inventory и лицензионные обязательства.

При запуске и возвращении в приложение выполняется проверка (повтор не чаще
15 минут). Полный выпуск имеет приоритет над Dart-патчем. При отсутствии
нового выпуска полоса скрыта; сетевой сбой фоновой проверки не создаёт ложную
ошибку VPN. Отказ предыдущей установки отображается отдельно после возврата
в приложение. Полоса высотой 24 px использует существующий размер окна.

Нажатие загружает пакет. Прогресс полного пакета основан на байтах; Shorebird
не предоставляет процент и использует неопределённый индикатор. Перед
перезапуском сохраняются подписки и оформление, блокируются команды VPN
и новые изменения UI. Запоздавший HTTP-ответ подписки не меняет сохранённый
список. Открытый диалог или ошибка сохранения откладывает перезапуск.

Полный пакет требует отключённого VPN/PROXY. Автоматическое отключение
не выполняется. Установщик использует отдельный атомарный запрос службы
для остановки только в состоянии покоя; активное соединение означает отказ.
Windows запрашивает UAC для установки в Program Files. Dart-перезапуск
не останавливает службу. На Android патч применяется при следующем обычном
запуске; принудительного завершения VPN/приложения не добавлено.

`exvpn-updater.exe` собирается закреплённым Go 1.27.2 без сторонних модулей
и поставляется рядом с UI. Адрес feed, канал, public key и текущая версия
закреплены внутри бинарника. Входящий stdin не принимает адресов, путей,
ключей или конфигурации подписок. Спецификация и ограничения:
[`native/appupdater/README.md`](../native/appupdater/README.md).

Для запуска из MSIX-процесса, включая Codex, учтено перенаправление AppData:
только фиксированная папка ExVPN может перейти к фактически открытому
системой приватному LocalCache. Проверяются совпадение File ID, ACL, точная
структура пути и удержание всех физических предков; глобальная проверка
reparse/path не ослабляется. [Контекст API Windows](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/ne-shlobj_core-known_folder_flag).

Проверки до выполнения установщика:

- HTTPS, разрешённый repository release asset и ограниченные redirect hosts.
- Отдельная подпись Ed25519 с domain separation, срок до 30 дней,
  приложение/платформа/канал, монотонный build и совместимая версия.
- Размер до 512 MiB, SHA-256, временная загрузка и повторная проверка staging.
- Закреплённые локальные пути, ACL, отказ reparse/hardlink, удержание файлов
  без разрешения записи/удаления до завершения установки.
- Обычный пользователь, точные путь/PID/время создания владельца, корректный
  выход UI и освобождение mutex. Процессы принудительно не завершаются.

Отделённый helper работает из cache, чтобы не мешать замене собственного
бинарника. Только проверенный установщик получает повышение прав; новое UI
открывается обычным пользователем. При отмене UAC или ошибке установки
предыдущее приложение открывается снова; восстановлением пакета занимается
существующий транзакционный установщик. Upgrade сохраняет прежний
`networkTesting`, если оператор явно не передал другое значение.

## Подготовка выпуска

Публичная конфигурация: `config/updates/windows-beta.json`. Закрытый seed
находится только в локальной `.private/`; его резервное копирование и CI
доступ оформляются отдельно, без добавления в Git. Старые data OTA/ключ
Shorebird не используются для подписи установщика.

После сборки immutable installer и проверки artifact.json:

```powershell
python scripts/release/sign-windows-update.py `
  --artifact <абсолютный-путь-к-installer.exe> `
  --url <HTTPS-release-asset-этого-репозитория> `
  --seed-file <локальный-seed-в-.private> `
  --output <новый-windows-x64.json>
```

Инструмент использует `cryptography==46.0.5`, работает офлайн, не выводит ключ,
не перезаписывает прежний manifest и ничего не публикует. Public key должен
совпасть с закреплённой конфигурацией, хеш — с artifact.json.

В этой итерации feed и новый публичный release не публикуются. Пустой/404 feed
не показывает «Доступно обновление». Полный цикл HTTPS → UAC → обновление →
повторное открытие, отмена UAC, восстановление после реального отказа и
проверка предыдущей версии остаются отдельными runtime gates. Подпись
manifest не является Authenticode-подписью издателя. Shorebird требует
соответствующей базовой сборки и опубликованного подписанного патча;
обычная Flutter-сборка не получает Dart OTA автоматически.
