# Windows: восстановление после изменения сети

Разработка для `0.1.0+10`; системная приёмка определяется отдельными отчётами.
Это частичный E1-008/E5, не завершённый gate клиента.

## Наблюдение на +9

В управляемом CLI Sandbox реальное отключение/возврат Ethernet сохранило
persistent WFP и блокировку независимого HTTPS-процесса. UI перешёл в
`reconnecting`, но HTTPS не восстановился автоматически за 75 секунд.
Старый монитор повторял запросы через прежний экземпляр ядра. После cleanup
адаптер включён, production binding/SCM восстановлены, TUN и guard отсутствуют,
route/DNS hashes совпали с baseline, прямой HTTPS вернулся.

## Контракт восстановления

- Однократно зарегистрированные read-only уведомления Windows отслеживают
  интерфейсы, адреса и default routes. Короткий down/up сохраняется как изменение
  сети; собственные TUN capture routes `/1` не запускают восстановление.
- Ошибка удалённого VPN-сервера при исправной локальной сети сохраняет живое
  ядро и прямой маршрут подтверждённых исключений. UI показывает восстановление;
  защищаемый трафик не переводится напрямую.
- При смене физической сети попытки идут с отменяемой задержкой 5/15/30 секунд.
  Сначала снимаются временные разрешения, затем закрываются сокеты и ядро.
  Persistent deny остаётся. Новый запуск заново получает защищённый DNS bootstrap
  и снимок интерфейса, создаёт TUN и только после HTTPS подтверждает соединение.
- Если новое исправное ядро пока не достучалось до сервера, оно продолжает
  обслуживать исключения. Во время замены ядра исключения временно блокируются.
  Ошибка teardown/guard приводит к `blocked`, а не к снятию защиты.
- Явное отключение отменяет ожидание, bootstrap и HTTPS. Старые результаты probe
  или статистики не публикуются для нового сеанса. Снимки профиля и исключений
  не меняются обновлением подписки. Таймер подключения начинается заново только
  после успешной проверки нового соединения.

## Сокеты и границы поколений ядра

В закреплённом Xray TUN каждый Start добавляет глобальный dialer controller,
а Close не удаляет его; ошибки этих callbacks стандартный dialer только
записывает в журнал. Собственный process-lifetime SystemDialer ExVPN возвращает
ошибку при невозможности привязать TCP/UDP socket к проверенному физическому
интерфейсу. Проверяются index/LUID, адрес, семейство, состояние, weak-host-send
и forwarding; политика ОС при этом не меняется.

Каждое ядро получает отдельный runtime token после построения доверенной
конфигурации. Он сохраняется при внутреннем копировании gRPC context, но не
попадает в подписку, сохранённый профиль или диагностику. Старый/неизвестный token
не может получить сокет следующего ядра. Перед новым поколением отменяются
незавершённые dial и закрываются учтённые TCP/UDP sockets. Системный DNS fallback
не разрешён. Sender/socket strategy допускается только `AsIs`: upstream `ForceIP`
вызывает глобальный resolver ещё до проверки поколения в SystemDialer.
Собственный dialer сначала проверяет token/context, затем сопоставляет только
точное имя выбранного endpoint с неизменным результатом защищённого bootstrap.
TLS SNI, HTTP Host и gRPC authority сохраняют исходное имя. Другие имена
отклоняются. Direct-исключения допускают только проверенные числовые TUN tuples,
включая отдельную проверку каждого UDP datagram.
Отдельные loopback tests проверяют фактический обмен TCP, WebSocket,
gRPC, XHTTP и Hysteria2; это не внешняя протокольная приёмка через Windows TUN.

## Открытое ограничение закреплённого Xray

Закрытие всех sockets не очищает upstream global caches gRPC `ClientConn` и
XHTTP `XmuxManager`: они удерживают объекты по свежему `MemoryStreamConfig`,
некоторые gRPC callbacks продолжают попытки. Изоляция token должна отклонять
их до DNS/сокета. Накопление metadata/goroutines при многократном создании ядра
остаётся отдельной задачей **EXVPN-E1-011**. Remote server outage не пересоздаёт ядро
каждый цикл, но долгий тест повторных смен сети и решение lifetime upstream
всё ещё нужны. Это не объявляется исправленной утечкой памяти.

Возможное отдельное решение — изолированный процесс ядра или проверенный patch
закреплённого upstream с явным закрытием transport caches. Небезопасная очистка
глобальных структур при ещё работающих goroutines не применяется.

В текущем pin нет публичного API удаления владельца кеша:
[gRPC map](https://github.com/XTLS/Xray-core/blob/701af60772cda123492f86e383e1fdba066614a9/transport/internet/grpc/dial.go#L47),
[XHTTP map](https://github.com/XTLS/Xray-core/blob/701af60772cda123492f86e383e1fdba066614a9/transport/internet/splithttp/dialer.go#L43),
[частичное Close клиента](https://github.com/XTLS/Xray-core/blob/701af60772cda123492f86e383e1fdba066614a9/transport/internet/splithttp/client.go#L182).
Предпочтительный следующий шаг — отдельный закреплённый patch с per-owner
retirement под mutex, запретом повторной вставки, закрытием gRPC ClientConn,
отменой XHTTP requests и полным учётом H1/H2/H3/raw-upload соединений.
Нужны race/lifetime tests и соответствующий изменённый source bundle;
текущий collector намеренно запрещает произвольные Go replacements.
Наличие тех же upstream globals в Android ещё не является Android runtime
доказательством утечки; отдельная проверка этой платформы остаётся открытой.

Windows Sandbox не поддерживает sleep/hibernate и имеет один сетевой адаптер:
проверка down/up не заменяет sleep/resume или переход между Wi-Fi и Ethernet.
Полный IPv4/IPv6/DNS packet capture, другие Windows версии и физические сети
сохраняются в CHECKLIST.md.
