# Подписанные обновления данных ExVPN

Дата: **2026-10-16**. Реализовано ядро механизма в `packages/exvpn_updates`.
Это не опубликованный OTA-сервис и не завершение E6: в приложении пока нет
production endpoint, доверенных production-ключей или автоматического применения.
Shorebird и обновление нативного пакета остаются отдельными механизмами.

## Контракт доверия

`TrustedUpdatePolicy` создаёт приложение. В ней закрепляются HTTPS URL manifest,
HTTPS базовый URL файлов, до восьми публичных Ed25519-ключей и точный список
разрешённых путей с лимитом каждого файла. Объекты и вложенные ключи копируются
в неизменяемые коллекции. Подписка, manifest и полученный файл не могут поменять
эту политику. В коде нет production-адреса или production-ключа по умолчанию.
Смена доверенных ключей требует изменения доверенной конфигурации приложения.

Пакет не запускает полученные файлы, не меняет системные разрешения, службу,
VPN-профиль или локальную политику маршрутизации. Допускаются только точные
allowlisted пути с расширениями `.json`, `.txt`, `.png`, `.webp`, `.dat`.
Абсолютные пути, обратный слеш, `..`, percent encoding, имена устройств Windows,
не-ASCII символы и варианты регистра отвергаются. Само расширение не доказывает
безопасность содержимого: приложение обязано передать `validateResource`, если
ресурс имеет семантические ограничения, и использовать данные только через
соответствующий ограниченный parser/renderer. Например, JSON правил не должен
становиться произвольной конфигурацией Xray.

## Формат публикации

HTTPS manifest endpoint возвращает UTF-8 JSON envelope ровно с тремя полями:

| Поле | Значение |
|---|---|
| `keyId` | ID одного из ключей, встроенных в доверенную политику |
| `manifest` | Base64 **точных UTF-8 байтов** manifest |
| `signature` | Base64 64-байтовой Ed25519-подписи этих байтов |

Проверяется подпись исходных байтов, затем разбирается JSON. Повторная сериализация
для проверки подписи не используется. Изменение даже пробела требует новой подписи.
Дублирующиеся ключи, неизвестные поля, неправильные типы и глубина JSON более 16
отвергаются. Поля собственно manifest:

| Поле | Условие |
|---|---|
| `format` | Целое число `1`; `1.0` не принимается |
| `revision` | Целое число от 1 до 2^53−1, строго больше локальной принятой ревизии |
| `channel` | `beta` или `stable`, точно совпадает с контекстом приложения |
| `minVersion` | Минимальная SemVer включительно |
| `maxVersionExclusive` | Верхняя SemVer исключительно |
| `minBuild`, `maxBuild` | Диапазон build number включительно |
| `files` | Полный набор файлов: объекты только с `path`, `size`, `sha256` |
| `rollbackOf` | Необязательная информационная ссылка на меньшую ревизию |

Семантика SemVer учитывает prerelease; metadata после `+` не меняет порядок.
`size` — точный размер в байтах; `sha256` — 64 строчных hex-символа. URL ресурса
строится только как `filesBaseUri.resolve(sha256)`; manifest не содержит URL файлов.
Manifest описывает полный снимок, но загрузчик скачивает только изменённые файлы.
Неизменённый файл повторно проверяется по хешу/размеру и копируется из текущего набора.
Дедупликации хранилища между снимками нет.

Дефолтные пределы: envelope 192 KiB, manifest 128 KiB, 64 файла, 4 MiB на файл,
32 MiB на снимок, 20 секунд на полный HTTP-запрос и 2 минуты на сетевую загрузку.
Политика может уменьшить пределы; абсолютные максимумы файла/снимка — 16/128 MiB,
запроса/сетевого бюджета — 1/5 минут. Общий бюджет ограничивает сетевые запросы;
он не является жёстким таймаутом файловой системы или пользовательского validator.

`HttpsUpdateTransport` проверяет обычную цепочку TLS и hostname, не следует
redirect, не принимает HTTP 206 или сжатый ответ, проверяет объявленный и фактический
размер потока. Таймаут охватывает весь ответ, затем HTTP client закрывается принудительно.
HTTP proxy из окружения не используется; это не обходит системный TUN/VPN.
Секреты и адреса не включаются в ошибки: наружу передаётся фиксированный `UpdateError`.
Подменяемый `UpdateTransport` и TLS factory предназначены для тестов и доверенного
host-кода, никогда не создаются из данных подписки.

## API и применение

`DataUpdateClient(policy, context, store, validateResource?)` предоставляет:

1. `recover()` — проверить подписи, совместимость и файлы сохранённых ревизий;
   вернуть текущий или предыдущий независимо проверенный набор.
2. `stage()` — получить и проверить manifest, загрузить изменённые файлы, проверить
   каждый хеш/размер и semantic validator, записать временный набор. Активная ревизия
   при этом не меняется. Возвращается `PreparedUpdate` со счётчиками скачанных и
   повторно использованных файлов.
3. `activate(prepared)` — повторно проверить staged-файлы и опубликовать ревизию.
   Вызывается host-приложением только в безопасный момент. Пакет сам не перезапускает
   приложение или VPN и не разрывает активное соединение.
4. `cancel(prepared)` — удалить staging и освободить writer lease.

Каждый успешно полученный `PreparedUpdate` необходимо передать в `activate` или
`cancel`. Повторное использование и передача другому клиенту отвергаются.
`activate` освобождает stage/lease и при успехе, и при отказе. `ActiveData.read(path)`
повторно проверяет размер/хеш файла; неподписанный путь прочитать нельзя.
Host заменяет собственный текущий `ActiveData` после успешной активации. Старые
ссылки нельзя сохранять бессрочно: после последующих активаций старые снимки удаляются.

## Диск, параллельность и восстановление

Корень `DirectoryUpdateStore` должен быть приватным каталогом приложения,
недоступным другим пользователям. Каналы имеют отдельные подкаталоги. Symlink
в проверяемых resource-компонентах не принимается; очистка не проходит по ссылкам
и допускает удаление только потомков своего канального каталога.
Защита от процесса того же пользователя, меняющего файлы между системными вызовами,
не заявляется: доступ к app-private каталогу — обязательная граница доверия.

Один writer lease держится от начала `stage` до `activate`/`cancel`. Для независимых
клиентов внутри одного Dart isolate используется registry по canonical root/channel,
для процессов — неблокирующий `FileLock.exclusive`. Конкурентный запрос немедленно
получает `busy`, а не ждёт завершения UI-решения бесконечно. **Все writers одного
корня должны работать в одном Dart isolate:** на POSIX advisory locks привязаны к
процессу, а static registry в Dart не разделяется между isolates. При необходимости
фонового isolate нужно передавать команды единственному writer через сообщения.
Завершение процесса освобождает OS lock. Забытый `PreparedUpdate` остаётся занятой
операцией до явного `cancel`/`activate` или завершения процесса.

Схема канального каталога:

```text
writer.lock
stage-<random>/...                   временный полный снимок
bundles/<manifest-sha256>/...        проверенный набор ресурсов
commits/r<revision>-<sha256>.json    подписанный envelope, маркер активации
```

Файлы записываются с `flush: true`. После повторной проверки staging переименовывается
в bundle. Затем записывается и flush-ится временный marker; его rename в **новое имя**
в том же каталоге — единственная точка публикации. Замена Windows current-pointer
с промежутком удаления не нужна. Неполные `.pending` и `stage-*` не активируются.
Сбой до публикации оставляет предыдущую ревизию. Ошибка последующей очистки не
превращает уже выполненную активацию в якобы неудавшуюся операцию.

После активации сохраняются текущий и последний проверенный предыдущий наборы.
Восстановление проверяет сохранённые подписи и файлы заново. Повреждение текущего
набора позволяет прочитать предыдущий, но локальный максимум revision не понижается.
Откат публикуется как новый подписанный manifest с **большей** revision и старым
содержимым; `rollbackOf` сам по себе не разрешает replay. Неоднозначные два marker
одной revision, более восьми committed-кандидатов или более 256 записей в каталоге
дают `corruptState` вместо неограниченного сканирования. Полное злонамеренное удаление
локального хранилища не защищено аппаратным monotonic counter.

Rename обеспечивает атомарную видимость на поддерживаемой локальной файловой системе.
Dart API здесь не делает fsync родительского каталога; гарантии при аппаратной потере
питания/повреждении файловой системы требуют отдельных платформенных испытаний.
Unit fault injection не заменяет эти испытания. Ресурсы не шифруются: они не должны
содержать пользовательские подписки, токены или приватные ключи.

## Проверка и зависимости

На Windows, Dart 3.13.5: **23 теста PASS**, `dart analyze` без замечаний.
Рабочее дерево; commit ожидается. Проверены:

- staging без преждевременного применения; повторное чтение новым клиентом; загрузка
  только изменённых файлов; cancel и запрет повторной активации;
- Ed25519 tamper, неизвестный ключ, неправильная подпись, типы/дубли JSON,
  traversal/зарезервированные имена, SemVer/build/channel и replay;
- неправильный хеш/размер, обрыв, semantic validator, ENOSPC на всех пяти границах
  записи/публикации, испорченный stage, manifest или текущий resource;
- предыдущая рабочая ревизия, rollback новой ревизией, неполные файлы и pruning;
- конкуренция двух клиентов и отдельного процесса без зависания;
- настоящий localhost HTTPS: доверенный только тестовым client-context сертификат,
  отказ default trust, redirect/206/compression, streamed-size limit и timeout.

Тестовый TLS-сертификат/RSA-ключ генерируется в памяти; CA не устанавливается в ОС,
проверка production TLS не ослабляется. Ed25519 test seed существует только в fixture.
Публикация по настоящему endpoint, интеграция с приложением, Android/Windows process-kill
и power-loss испытания OTA, release signing и Shorebird ещё не выполнены.

Закреплены `cryptography 2.9.0` (Ed25519, Apache-2.0), `crypto 3.0.7` (SHA-256,
BSD-3-Clause), test-only `pointycastle 4.0.0` (TLS fixture RSA, MIT). Lock-файл и
копии LICENSE входят в пакет. Полный состав runtime notices после интеграции должен
собираться из фактически разрешённых зависимостей приложения.
